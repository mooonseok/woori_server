# 공통 설계 — 확정 사항과 구현 제안

## 유지할 제품과 구조

앱 이름은 우리. 가족·지인 몇 그룹으로 시작한다. 깔끔하고 세련된 사진 갤러리,
큰 사진·여백·읽기 쉬운 글자, 홈/앨범/마이페이지 3개 탭을 유지한다.
새 기능도 v6 기반 UI와 container/view, hooks/services, Atomic 구조를 따른다.
사진 뷰어는 핀치·더블탭·팬을 우선하고 버튼을 늘리지 않는다. 뒤로 가기는 페이지명 없이 아이콘.
검색 펼침·도구 표시·정렬 드롭다운·단계별 가이드에서 포커스와 reduced-motion을 검증한다.
모든 화면에 초기/로딩/실패/권한 없음 상태를 두며 API 실패를 샘플 데이터로 대체하지 않는다.

client: Next.js 정적 export 웹 + 관리자 웹 + 향후 Capacitor 앱.
server: NestJS API + 독립 워커, Prisma/PostgreSQL, OpenAPI 정본.
배포 목표: Railway 유료 API/워커(상시 실행), Supabase Pro, 비공개 R2.
웹 정적 호스팅 제공자는 아직 선택하지 않았다. 요금·상품 조건·스토어 요건은 실제 적용 시 공식 문서로 재확인한다.

## 공통 보안 경계

- 그룹의 현재 활성 멤버십을 매 요청 검사한다. 인증만으로 사진 접근을 허용하지 않는다.
- 웹은 HttpOnly 세션 쿠키, Origin/CSRF 검사. 서버 DB 역할과 migration 역할은 분리한다.
- RLS의 서버 역할 허용은 사용자별 권한을 대신하지 않는다. 쿼리에서 사용자·그룹 범위를 강제한다.
- 탈퇴/정지/내보내기/사진 삭제와 동시에 진행되는 조회·업로드·푸시를 경쟁 조건으로 검증한다.
- R2는 private, 읽기는 권한 확인 API를 통한다. 원본 URL·토큰·메일 본문을 로그에 남기지 않는다.
- 푸시는 현재 구현의 outbox, 세션 연결, bindingVersion, 발송 lease, 표시 재검증을 재사용한다.
  웹 푸시 구현을 Capacitor 네이티브 푸시 완료로 취급하지 않는다.

## W01 계정 복구와 이름 수정 (다음 구현안)

화면: 로그인 → 아이디 찾기 / 비밀번호 재설정. 이름+이메일만 입력.
일치 계정 유무와 무관하게 같은 202/안내 문구를 돌려주고, 실제 메일만 해당 계정에 발송한다.
HTTP 오류는 요청 제한·서비스 장애처럼 사용자가 대응할 수 있는 범주로 구분한다.
아이디는 메일 본문으로 안내한다. 비밀번호는 원문/임시 비밀번호를 메일로 보내지 않고
일회용 링크를 보내 새 비밀번호를 직접 입력한다. 이 복구 UX는 기존 기획의 권장안이며 구현 전 사용자 확인 대상이다.
이름은 신원 증명이 아니라 조회 보조값이다. 현재 DB displayName 기준 사용 여부와 이름 변경 시 복구 안내를 확정한다.

제안 API (OpenAPI 변경 전에 확정):

- `POST /v1/auth/recovery/username` {name,email} → 일반화된 202.
- `POST /v1/auth/recovery/password` {name,email} → 일반화된 202.
- `POST /v1/auth/recovery/password/confirm` {token,newPassword} → 204, 자동 로그인하지 않음.
- `PATCH /v1/auth/profile` {displayName} → 갱신된 사용자. 이메일/아이디 변경을 섞지 않음.

서버: 기존 이메일 확인 token과 복구 token을 용도별로 분리한다. 신규 모델 또는 목적 enum을 검토하고
해시·사용 시각·만료·계정 연결을 저장한다. 만료 30분은 제안값이다. 이전 링크 무효화 정책을 확정한다.
동일 token 소비·비밀번호 변경·모든 기존 세션 및 연결된 푸시 구독 폐기를 한 트랜잭션으로 처리한다.
성공 후 이전 복구 token도 무효화한다. 두 동시 확인 중 하나만 성공해야 한다.
요청 제한은 IP 및 정규화한 이메일의 해시 등으로 적용하고 원문 이메일을 rate key로 노출하지 않는다.
메일 클릭 GET은 token을 소비하지 않는다. 프리뷰/보안 스캐너에 의해 비밀번호가 변경되면 안 된다.
클라이언트는 token을 저장소/분석 로그에 기록하지 않고 URL에서 읽은 뒤 주소 노출을 줄이며
재설정 페이지의 referrer 정책·외부 리소스를 점검한다.

## W02 그룹 관리

활성 회원 목록/그룹명 수정/탈퇴/내보내기/소유권 이전/그룹 삭제를 단계별로 구현한다.
일반 회원은 자신만 탈퇴, 그룹장은 내보내기 가능. 마지막 그룹장은 소유권 이전 또는 그룹 삭제 후 탈퇴.
소유권 이전 대상은 같은 그룹의 활성 회원이며 서버 트랜잭션에서 기존 소유자와 대상 상태를 재검사한다.
비회원에게 명단을 노출하지 않는다. 권한 상실 즉시 사진·댓글·추억·알림·푸시 대상에서 제외한다.
그룹 삭제는 기존 사진 삭제 큐와 quota 정합성을 재사용하고 대량 객체 삭제를 요청 안에서 끝내지 않는다.
기존 기획의 ‘앨범 생성자 제목 수정’과 현재 ‘그룹장 수정’ 차이는 결정을 받아 통일한다.

## W03 촬영일과 추억 홈

현재 홈은 대표 앨범 커버/최근 앨범이며 날짜 기반 추억 API는 없다.
서버가 선택 그룹 + 현재 멤버십 기준으로 N년 전 오늘/같은 달 후보를 선택한다.
촬영일·업로드일·사용자 지정일과 출처를 분리하고 날짜가 없으면 업로드일 기반이라고 표시한다.
회전 보정 전 EXIF 날짜를 읽되 GPS를 노출하지 않는다. 신뢰할 수 없는 EXIF 날짜/타임존은 검증한다.
기존 사진의 일괄 재해석은 별도 백필 계획/승인 대상이며 원본을 몰래 순회하지 않는다.
윤년·자정·타임존 경계와 같은 사진 중복, 개인별 숨김을 처리한다.
추억 푸시는 홈과 별도 선택 기능이며 기본 자동 발송으로 추가하지 않는다.

## W04 사진 처리와 모바일 품질

HEIC는 현재 미지원이다. 실제 디코더/배포 이미지 지원을 작은 샘플로 먼저 확인하고 라이브러리 도입을 결정한다.
MIME와 magic bytes, 크기/픽셀/메모리/처리 시간 제한, EXIF orientation과 위치 댓글 좌표를 함께 검증한다.
원본 보존과 GPS가 없는 파생본 정책을 유지하되 원본 다운로드 시 EXIF 포함 안내 정책을 확정한다.
현재 완료 API의 동기 처리에서 영구 처리 큐로 옮길 때 READY 전환·quota·삭제 경합·idempotency를 보존한다.
중단/부분 실패/재시도/중복 파일 정책과 모바일 저장 UX를 검증한다. 앱 종료 후 계속 전송을 약속하지 않는다.
고아 객체 정리는 staging lifecycle와 DB-객체 대조를 구분하고 report-only → 검토 → 제한 삭제 순서로 도입한다.

## W05 계정 수명과 서비스 안내

로그인 중 비밀번호 변경은 현재 비밀번호 재확인. 이메일 변경은 새 주소 확인 전까지 기존 주소 유지,
성공 시 구 token 정리·기존 주소 통지·세션 처리 정책을 결정한다.
회원 탈퇴와 그룹 탈퇴를 분리하고 소유 그룹 이전, 공유 사진/댓글 처리, 보관 기간을 먼저 확정한다.
상태 전환과 접근 차단은 즉시, R2/DB 실제 삭제는 재시도 가능한 작업으로 분리한다.
공지/도움말/문의/개인정보 안내/신고·차단을 제공하고 차단이 공동 앨범 가시성에 미치는 영향을 정의한다.
보관 기간과 법적 문구는 임의 확정하지 않는다.

## W06 관리자

별도 관리자 인증 audience와 MFA/재인증, 최소 역할 권한을 적용한다.
회원/그룹/앨범 목록은 필요한 메타데이터만 노출하고 사진 열람은 명시적 권한·사유·감사로그가 있어야 한다.
일반 회원 세션의 관리자 호출은 항상 거절한다. 운영자는 비밀번호 원문 조회 불가.
회원 수정·정지·탈퇴 처리는 일반 도메인 정책과 큐를 재사용하고 감사 이벤트에 비밀값을 넣지 않는다.
공지/신고 처리와 운영 지표(처리 큐·메일·푸시 실패·저장량)를 추가한다.

## W07 안정성 및 가족 베타 배포

메일 outbox는 인증/복구 메일의 DB 변경과 원자적으로 연결하고 worker 재시작·재시도·만료를 설계한다.
메일 전송에 필요한 token 원문은 hash만으로 재구성할 수 없으므로, payload 암호화와 짧은 보관·폐기를 함께 설계한다.
공급자 timeout 후 재발송 중복을 고려하고 idempotency 지원 여부를 확인한다.
API/worker 각각 health와 실패율, queue lag, DB/R2/메일 장애를 감시한다.
웹과 API 도메인·쿠키 SameSite/Secure·CORS·프록시 hop·R2 PUT CORS를 실제 배포 토폴로지로 검증한다.
새 migration 먼저, 호환되는 API/worker, 웹 순으로 배포하며 파괴적 migration은 별도 절차로 한다.
운영 DB에는 로컬 dev:db:prepare나 통합 테스트를 실행하지 않는다.
DB와 R2 백업을 분리하고 별도 환경에서 복원 훈련으로 접근 제어·참조·사진 실물을 확인한다.
RPO/RTO·보관·비용 한도는 사용자 결정. 알림·반응 묶음 발송 정책은 중복 제거와 함께 결정한다.

## W08 앱 배포

Capacitor 설정/의존성 존재와 스토어 출시를 구분한다. iOS·Android 실기기에서
사진 선택/저장/권한 거절/복귀, 초대 Universal/App Links, 설치 전후 초대 복원을 검증한다.
설치 후 토큰 자동 복원을 보장하지 않고 같은 계정 로그인 또는 초대 링크/코드 재진입을 제공한다.
네이티브 세션/refresh rotation 및 FCM/APNs token lifecycle를 웹 인증과 구분해 설계한다.
FCM/APNs 키·앱 식별자·서명·개발자 계정은 별도 비공개 설정이다.
스토어 제출 전 계정 삭제·신고/차단·개인정보·접근성 요구를 공식 자료로 다시 확인한다.

## 구현 전 결정 목록

W01: 복구 링크 UX, 이름 변경과 복구 조회 기준, token 유효기간/재요청 정책.
W02: 앨범 제목 수정 권한, 그룹 삭제·탈퇴 시 콘텐츠 처리.
W03: 날짜 우선순위/타임존, 과거 사진 백필, 추억 숨김·알림 기본값.
W04: 원본 EXIF 안내·파일/픽셀/묶음 한도·디코더 선택.
W05: 탈퇴 보관 기간·차단 범위·정책 문구.
W06: 관리자 역할·사진 열람 허용 범위·감사 보관 기간.
W07: 정적 호스팅·도메인·리전·백업 목표·비용 한도·실서비스 메일 도메인.
W08: 앱 식별자·스토어 계정·네이티브 로그인/푸시 구성.
각 결정은 해당 W 구현 전에만 확인한다. 모두를 한 번에 질문하여 W01 시작을 막지 않는다.
