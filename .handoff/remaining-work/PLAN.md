# 실행 계획과 완료 기준

각 단계는 server 계약/정책 → client 연결 → 두 계정 검증 → 리뷰 순서로 진행한다.
아래는 권장 순서이며 W07 환경 조사는 병행 가능하다. 기능 구현은 해당 작업 요청을 받은 뒤 시작한다.

| ------------------ | --------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------- |

| W02 그룹 수명      | W01 이후 권장               | 명단/그룹명/탈퇴/내보내기/그룹장 이전/삭제             | 두 회원+비회원 권한표, 마지막 그룹장·동시 이전·삭제 경합, R2 정리           |

## 각 작업 공통 완료 체크

- [ ] 현재 동작/미구현과 결정사항을 확인하고 필요한 결정만 사용자와 확정.
- [ ] API 계약, 서버 권한·DTO, client 소비자 변경을 같은 작업으로 추적.
- [ ] DB 적용 필요 시 migration 작성과 적용을 구분. 대상 환경/영향/복구 방법을 기록.
- [ ] 성공/실패/빈/로딩/중복 입력/계정 전환/권한 상실/네트워크 지연을 검증.
- [ ] unit·integration·browser 결과를 명령/날짜/환경/통과 범위로 기록.
- [ ] 실제 외부 연동을 mock 결과로 대체해 보고하지 않음. 미실행 항목은 남김.
- [ ] 테스트 계정/사진/R2 객체/서버는 해당 작업 소유분만 정리.
- [ ] `project.json`, OpenAPI, 해당 코드/테스트에 유지해야 할 최종 사실을 반영.
- [ ] status.json의 해당 작업만 done으로 갱신. 다른 작업을 한꺼번에 완료하지 않음.

## 다음 세션 운영 준비 순서

1. status.json 최신 근거와 두 저장소 Git 상태를 확인한다. W01–W03을 다시 구현하지 않는다.
2. `fix/production-readiness`의 동영상 API 전달 보완과 브라우저 미검증 범위를 확인한다. Chrome 로컬 접속 차단을 해결한 뒤 회원·관리자 재생·구간 이동·다운로드·권한 회수를 검증한다.
3. Supabase Pro 서울 DB의 직접 검증 기록과 2026-10-19 사용자가 보고한 Lightsail 서울 API·워커 Docker 실행, 운영 R2 설정, Pages `woori.stream` 로그인 화면 확인을 구분해 확인한다. 기존 리소스를 다시 만들지 않고 운영 수용·관리자 웹·백업 준비의 미확인 항목을 점검한다. 계정·결제·비밀 입력은 사용자 담당이다.
4. 운영 브랜치와 일일 백업 서비스·실패 알림 설정을 확정한다. 새 서비스 생성·원격 배포는 별도 승인을 받는다.
5. 2026-10-16 적용된 운영 migration 19개와 woori_api/TLS 검증 기록을 확인한다. 후속 migration만 변경 대상·영향·복구 방안을 확인하고 승인 범위에서 적용한다.
6. 같은 커밋의 API·워커 → 호환되는 웹·관리자 순서로 배포하고 HTTPS·메일·푸시·영상·백업/복원 수용 결과를 기록한다.
7. W04/W05 실기기 및 접근성, 미정 운영 정책을 확인한다. W08은 W07 이후 별도 결정부터 진행한다.
8. W01–W08 전체 완료 조건 전에는 CLEANUP을 실행하지 않는다.

## 알려진 정책 차이와 빠진 구현 확인

- 초기 기획 ‘아이디 또는 이메일 로그인’과 실제 로그인 API의 지원 범위를 확인해 W01 범위를 결정한다.
- 앨범 생성자 수정/그룹장 수정의 기획·구현 차이는 W02에서 확정한다.
- 앨범 커버/기간 편집, 검색·정렬, 가이드/제스처의 실제 모드 완성도는 W03/W04에 감사 항목으로 포함한다.
- 그룹 승인제·가입 알림, 추억 푸시, 반응·업로드 묶음은 enum/설정 존재만으로 완료 처리하지 않는다.
- 기존 모바일 기기 테스트 미완료는 W04/W07/W08에 남긴다.
- W07은 가족 베타, W08은 스토어 단계다. 스토어를 후순위로 두어도 status에서 생략하거나 done으로 표시하지 않는다.

## 결과 기록 규칙

status.json의 각 작업은 pending → in_progress → done만 사용한다.
완료 시 evidence에 실제 검사·환경·결과를 쓰고 implementationRefs에 관련 commit/PR을 적는다.
peerEvidence에는 상대 저장소 계약/통합 검증 근거를 기록한다.
유보/보류는 done이 아니다. 범위를 바꾸려면 사용자 결정을 기록하고 이 인계 범위를 다시 설계한다.
수치·기기 검증을 추정하지 않는다. 비밀번호·token·개인 메일 주소·사진 URL을 근거에 넣지 않는다.
