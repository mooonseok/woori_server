---
name: woori-verify
description: 변경 위험에 맞는 실제 프로젝트 검사와 회귀 검증을 선택하고 결과를 보고한다.
---

1. 입력은 원래 요구사항·수용 기준·변경 범위·기준 커밋/기존 diff·허용된 환경이다. 저장소 루트에서 `.nvmrc`/`packageManager`, `package.json`, 실제 검사 구현을 확인한다.
2. `pnpm harness:check`로 전제를 확인하고 `pnpm harness:verify --profile <이름> --dry-run`으로 설정과 예정 명령을 확인한다. dry-run은 검사를 실행하거나 환경 준비 여부를 점검하지 않으며, 프로필별 환경 전제는 실제 verify 실행에서 확인한다. 아래 프로필은 검사 선택의 출발점이며 실제 실행 목록은 `scripts/policy/verification-profiles.json`이 정본이다.
3. Node/pnpm 버전과 기존 node_modules가 필요하고 정책 TOML 검사는 Python 3.11+의 tomllib을 사용한다. 준비가 됐으면 같은 명령에서 `--dry-run`을 빼고 실행한다. 실행 위치는 해당 저장소 루트다. 의존성 설치·환경 준비·서버 시작·배포를 하네스가 대신 수행한다고 가정하지 않는다.

| 프로필        | 선택 기준                     | 검증 범위                                    |
| ------------- | ----------------------------- | -------------------------------------------- |
| `policy`      | 하네스·역할·스킬·훅 검사 변경 | 정적 연결과 정책/하네스 fixture 검사         |
| `server-unit` | API/공통 순수 로직 변경       | Prisma·타입·단위 검사                        |
| `server-db`   | 인증·권한·DB 동작 변경        | 기존 격리 로컬 DB 통합 검사                  |
| `worker`      | 워커 변경                     | 빌드와 워커 사전 검사; 실제 작업 처리는 별도 |
| `full`        | 여러 영역에 걸친 제출 전 검증 | 기존 전체 품질 검사; 로컬 DB 전제 포함       |

- `server-db`와 `full`은 로컬 검증 범위에서만 실행한다. `scripts/run-integration.mjs`의 부모 주소 제한 `127.0.0.1:55439/woori_dev`를 유지하고 별도 `woori_test_*` DB 생성·정리를 사용한다. 기존 DB에 테스트를 실행하지 않는다.
- 로컬 DB 주소가 허용 범위를 벗어나거나 포트에 접속할 수 없으면 blocked로 보고한다. 실제 DB 인증·런타임 역할 권한은 통합 검사에서 확인하며, 실패 원인은 로그를 조사해 분류한다. 하네스가 Docker 시작, `dev:db:prepare`, migration/grant 적용을 자동으로 수행하게 만들지 않는다.
- `worker` 사전 검사 성공은 실제 R2·메일·푸시·작업 처리 성공을 뜻하지 않는다. 네트워크/외부 상태가 필요한 검증은 범위를 별도 확인한다.

4. 변경 위험에 맞는 추가 검사를 수행한다. 경계·실패·경쟁 조건을 확인하고 구현 문자열을 복제하는 검사나 테스트 삭제/약화로 통과시키지 않는다. 작은 변경에 전체 검사를 기계적으로 반복하지 않는다.
5. 결과를 `pass`(실행 성공), `fail`(실행 실패), `blocked`(환경/실행 조건 때문에 완료 못함), `not-run`(실행하지 않음)으로 구분한다. 성공 기준은 관련 명령의 종료 코드 0과 수용 기준 충족이다. 환경 차단·미실행은 통과가 아니다.
6. 기존 상태에서 같은 조건으로 재현한 근거가 있어야 기존 실패라고 분류한다. 근거가 없으면 미확인으로 남긴다. 실패 시 woori-debug를 적용하고 동일 실패가 두 번 반복되면 원인·시도·다음 선택지를 정리한 뒤 재시도를 중단한다. 러너의 반복 감지는 검사 단계와 종료 코드에 기반하므로 원인이 같다는 증거는 아니다. 두 번 실패한 뒤 다음 실행은 차단된다. 분석 후 새로운 가설로 재검증해야 한다면 `--retry-reason "확인한 원인과 다음 가설"`을 전달한다. 러너는 이 값을 보고서에 저장하지 않는다. 셸 기록이나 pnpm 명령 표시에는 남을 수 있으므로 비밀값을 넣지 않는다. 분석 근거는 대화에 남기고, 이 옵션으로 실행 권한이나 허용 명령이 늘어나지는 않는다.
7. 하네스는 커밋·작업 트리 식별자와 검사 요약을 `os.tmpdir()/woori-harness` 아래 비공개 파일로 기록한다. 원본 자식 프로세스 로그와 비밀값은 저장/출력하지 않는다. 실패 로그가 필요하면 해당 명령을 통제된 환경에서 다시 확인해 비밀값을 제외한 오류 요약만 공유한다. 보고서는 실행 당시 증거이며 코드/환경이 달라지면 과거 성공을 재사용하지 않는다.
8. 반환은 실행 위치·명령·결과·종료 코드·오류 요약·보고서 위치·미실행 항목·남은 위험이다. 결과를 확인한 메인 에이전트가 수정/검토/완료 단계를 결정한다. `policy:check` 성공은 실제 Codex 역할 활성화나 훅 신뢰를 증명하지 않는다. 네이티브 설정 확인은 `references/policy-operations.md`를 따른다.
